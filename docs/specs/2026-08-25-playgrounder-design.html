playgrounder — design spec

A Flutter package that extracts flutter_flowin's playground affordance — a component rendered live beside the knobs that configure it — into a design-system-agnostic package. Written 2026-08-25.

Purpose

flutter_flowin ships a FlowinPlayground<T>: a component previewed live beside a docked inspector of presets, knobs, and actions. It is already generic on the caller's config type, but every file imports flutter_flowin for three things — a few chrome widgets (tab row, preset button, action button), spacing/border tokens, and ColorScheme sugar.

playgrounder lifts that affordance out so any package can present a component the same way, without inheriting a design system. The driving first consumer is the lowframer example app, which wants a live preview + knobs to demonstrate its wireframe arts. flutter_flowin is the second consumer and the injection case study: it swaps its own widgets in through a PlaygroundStyle seam.

Scope: the playground affordance only. The gallery/showcase shell — scaffold, entry model, cover-art tiles, fade tabs, capped app bar — belongs to flutter_flowin and is not part of playgrounder. What is extracted is preview + inspector + knobs, because that is the piece with two real consumers (flowin has it; lowframer's example wants it). The shell has one consumer and stays home.

Why a new package and not just widgetbook

widgetbook is the closest prior art: use-cases, knobs read via context.knobs, addons for global state. Two differences make it the wrong fit here, and both clarify what playgrounder is:

  • widgetbook is a terminal app, playgrounder is an embedded affordance. You run widgetbook; you do not embed its panel inside your own app and restyle it. playgrounder is meant to drop into a consumer's screen (the lowframer example, a flowin showcase page) and adopt that consumer's chrome. widgetbook owns all its chrome and never lets you substitute it — so it offers no answer to the one thing playgrounder must do.
  • widgetbook's knob indirection buys URL state we do not need. A widgetbook Knob<T> declares fields and a valueFromQueryGroup so knob state round-trips through the URL for shareable deep links. playgrounder has no URL-state requirement in v0.1.0, so its knobs are plain widgets that build a Slider/Switch directly — lower ceremony. Persistence, if it ever lands, would revisit the knob contract; that is a named deferral, not a seam we pre-build.

Architecture

Package playgrounder, new repo ~/Work/Projects/playgrounder. Dependencies: Flutter SDK and equatable (flowin's existing choice for the preset value type; widely used, kept). The package imports no design system and no Material component beyond raw primitives used as scaffolding (Slider, Switch, TabBar, Divider, FilledButton).

Package name carries the -er house coinage (as lowframer does); the public classes keep the clean Playground noun.

The style seam

PlaygroundStyle is how a design system dresses the playground — a subclassable class, not a bag of nullable function fields: defaults live in the base method bodies, a consumer overrides only what it wants, and the widget tree calls the style unconditionally with no null-checks. Three of its members build widgets; the fourth returns the stage color. This is the seam that lets flowin adopt playgrounder while bringing its own design system — the thing widgetbook has no equivalent for.

class PlaygroundStyle {
  const PlaygroundStyle();

  /// Presets/Custom tab row. Default: Material TabBar over [labels].
  Widget buildTabs(BuildContext context, {
    required TabController controller,
    required List<String> labels,
  });

  /// One preset row. Default: full-width FilledButton.tonalIcon,
  /// icon = check when selected.
  Widget buildPresetRow(BuildContext context, {
    required String label,
    required bool selected,
    required VoidCallback onPressed,
  });

  /// One pinned action. Default: full-width FilledButton.tonalIcon.
  Widget buildActionButton(BuildContext context, {
    required String label,
    Widget? icon,
    required VoidCallback onPressed,
  });

  /// Preview stage background. Default: surfaceContainerHighest.
  Color stageBackground(BuildContext context);
}

The four points are exactly where flowin's version reached for flowin widgets or a scheme-specific color: the inspector tab row (FlowinTabs), the preset button (FlowinItemButton.tonal), the action button (FlowinButton.tonal), and the stage tint.

Why stageBackground lives on the style. It is the fourth per-design-system injection point, cohesive with the other three — and a Style holding a color is natural, so the earlier "a builders class returning a Color is a stretch" concern is gone. flowin's stage defaults to outlineVariant rather than a container role because the flowin scheme leaves surfaceContainer* at plain surface — pure white, so a white subject vanishes (flowin_pm#33). That is a design-system fact, wired once in flowin's builders rather than repeated at every call site. playgrounder's own default is surfaceContainerHighest (a real tint under a stock Material scheme). The per-call previewBackground on the playground still wins over the builders for a specific neutral subject.

Everything else stays raw Material deliberately (Slider, Switch, Divider, textTheme): a knob is scaffolding for driving a demo, not a thing being demonstrated — the same doctrine already stated in flowin's source.

The spacing knob transform

flowin's FlowinPlaygroundSpacingKnob is ~97 LOC, most of it a SpacingStep enum resolving against context.spacing. It does not survive as a widget. playgrounder ships ScaleKnob over a dumb ScaleStep model instead. When flutter_flowin later migrates, it builds the list where the theme is in scope, inside its knobsBuilder:

knobsBuilder: (context, config, onChanged) {
  final s = context.spacing;
  final steps = [
    ScaleStep('none', s.none),
    ScaleStep('xxs',  s.xxs),
    // ...
  ];
  return ScaleKnob(label: 'Gap', values: steps, ...);
}

Theme resolution stays flowin-side, so the "a demo cannot quote a stale pixel" property is preserved. playgrounder stays free of any scale semantics.

Consumers and delivery order

Two real consumers exercise the two paths:

  • lowframer example app — the driving consumer. Uses the default Material path (no PlaygroundStyleScope): lowframer is a Material-native wireframe kit, so its example wants playgrounder's stock chrome. This is the live proof that the zero-config path is genuinely usable.
  • flutter_flowin — the injection case study. Its showcase playground pages wrap the subtree in a PlaygroundStyleScope whose style returns FlowinTabs, FlowinItemButton.tonal, FlowinButton.tonal, and outlineVariant. Proves a design system can adopt playgrounder without inheriting Material chrome.

Delivery order

  1. Build the playground affordance in the playgrounder repo (package + its own example).
  2. Wire the lowframer example against it immediately via a path (or git) dependency, so the affordance lands in the lowframer example now — that is the actual motivation — and doubles as validation before publish.
  3. Once both the playgrounder example and the lowframer example validate it, publish playgrounder; swap lowframer's path dep to the pub version.

This ordering means the affordance you wanted (live preview + knobs in the lowframer example) exists during development, not only after playgrounder ships. The path dep is the dev-time bridge; the pub version is the release-time swap.

playgrounder's own example app

example/lib/main.dart is a single playground with stock Material chrome — playgrounder's zero-config path. The whole screen is the playground: no app shell, tabs, or navigation compete with the preview and inspector, because those framing pieces belong to a consumer's app, not to the playground affordance itself. The example depends only on playgrounder; it does not depend on flutter_flowin.

The PlaygroundStyle injection path is documented in the README and proven live by the lowframer example (which consumes playgrounder), so the package's own example stays focused on what playgrounder is rather than on how one design system adopts it.

The demoed subject exercises every public symbol: a small card config driven by two switch knobs and a scale knob, grouped under a KnobGroup, with two presets and one "copy config" action.

Testing, CI, infra

Clone lowframer's template exactly: .fvmrc pinned to Flutter 3.44.0, the same analysis_options.yaml, a CI workflow with a package job gated at 100% line coverage and an example job that is analyze-only, a version_drift_test.dart covering every version spot (pubspec, README install snippet, CHANGELOG), and a CLAUDE.md carrying the same hard gates. History is a single amended commit until the first real release.

Key tests

  • Breakpoint: stacks below 900px, docks beside above it.
  • Preset matching: active preset resolves by ==; moving a knob drifts to Custom.
  • Relevance: an irrelevant knob / group renders SizedBox.shrink, not a disabled control.
  • Presetless playground: the TabController is built in initState, not a lazy late final — flowin hit a dispose-time ticker crash when presets were empty and the tabs never rendered. Keep the fix; add the regression test flowin never wrote.
  • Default style vs injected style: with no scope, buttons are Material; with an injected PlaygroundStyle, its widgets appear.
  • ScaleKnob readout renders 'name — Npx'.

Hard gates (from both repos' CLAUDE.md). Never run dart pub publish without a separate explicit approval of that exact step — dry-run, show output, stop. Do not push branches or open PRs before the user validates in the running app. Edit and git commit go in separate tool calls (the pre-commit hook misparses a heredoc followed by a commit). Every Dart/Flutter command through fvm.

Milestone

playgrounder v0.1.0 = the playground affordance (preview + inspector + presets + actions), the five knob symbols, the PlaygroundStyle seam with Material defaults, and a two-tab example documenting both the bare path and the flowin injection path.
